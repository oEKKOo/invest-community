## 1. 工程背景与目标

投资社区类系统在后端侧典型压力包括：

- **同一页面多次 HTTP 调用**：首页、个人主页若拆成大量细粒度 REST 资源，前端并发请求多、总耗时长。
- **ORM N+1 查询**：列表带作者、带点赞状态、带嵌套评论时，`SerializerMethodField` 逐条查库易导致 SQL 次数随行数线性增长。
- **列表响应体积过大**：列表接口返回正文全文、大字段嵌套，带宽与序列化成本高。

本项目在本科毕设可维护范围内，以「**列表与详情分离**、**批量预取互动状态**、**适度页面级聚合**」为主线落地后端优化，并与前端 `excerpt` / `content` 字段约定对齐。

## 3. 既有后端能力（优化专项之前已形成的基础）

以下能力在「接口与查询性能」专项之前已存在于代码库或各模块文档中，构成后端非功能需求的**基线**。

### 3.1 聚合接口与缓存（首页概览）

- **`GET /api/dashboard/overview/`**：合并热门帖子、热门公开组合、社区统计、图表用 `marketSeries` 等，减少首页完全依赖多次独立列表接口。
- 使用缓存键区分匿名/登录用户（如 `user_key`），TTL 可由 `DASHBOARD_OVERVIEW_CACHE_TTL` 等配置控制。
- 热门帖子、组合查询侧已使用 **`select_related` / `prefetch_related`** 降低作者、资产等关联查询次数。

### 3.2 各模块中的查询预取（零散但重要）

- **内容列表、资产下帖子、组合列表**等视图在演进过程中已多处使用 `select_related('author')`、`prefetch_related('assets', 'boards', …)`。
- **管理端、举报、组合评论**等路径在各自模块总结文档中曾记录潜在 N+1 或深层序列化风险（见 `docs/` 下各模块代码总结），与本专项形成对照。

### 3.3 行情榜单与快照

- **`GET /api/market/rankings/`** 基于 `AssetQuoteSnapshot` 子查询取最新快照，并带缓存与索引设计（见 `market_data` 迁移与视图注释）。

### 3.4 请求耗时日志

- 部分接口使用 `@timed_api` 等装饰，便于在日志中按 `endpoint` / `duration_ms` 检索。

> **说明**：上述基线并不保证「列表点赞状态」「转发数」「评论点赞」等全部为批量查询；**专项优化**主要针对这些薄弱点系统化处理（见第 4 节）。

## 4. 接口与查询性能专项（本轮落地内容）

本轮优化对应「列表瘦身 + 批量互动状态 + 评论批量点赞 + 详情补全关联 + 聚合接口扩展 + 榜单逻辑复用」，与实现代码一致。

### 4.1 列表与详情分离：`ContentCardSerializer`

| 维度 | 说明 |
|------|------|
| **列表/卡片** | 使用 `ContentCardSerializer`：主文字段为 **`excerpt`**（由正文截断生成，约 320 字），不再在列表中返回全文 **`content`**。 |
| **详情** | `ContentDetailSerializer` / `GET /api/posts/{id}/` 仍返回全文 **`content`**（映射模型 `body`），保证阅读与编辑场景。 |
| **内嵌标的/板块** | `AssetCardSerializer`、`BoardCardSerializer` 仅保留列表展示所需字段，避免 `description`、`finnhub_symbol` 等在每条卡片重复传输。 |
| **投票摘要** | `PollCardSerializer` 用于卡片场景，减轻列表负载。 |

### 4.2 批量预取帖子互动状态与转发数（消除列表 N+1）

- 工具模块：[`background/content/post_list_helpers.py`](../background/content/post_list_helpers.py)  
  - **`build_post_card_context(request, post_ids)`**：对当前页帖子 ID 批量查询点赞、收藏，并聚合 **`Repost`** 得到 `repost_counts`，写入序列化 context（`liked_post_ids`、`favorited_post_ids`、`repost_counts`）。
- 序列化：[`PostInteractionMixin`](../background/content/serializers.py) 统一 `get_isLiked` / `get_isFavorited` / `get_reposts`：优先使用 context 中的集合与字典，**避免对每条帖子 `exists()` 或 `reposts.count()`**。
- **转发数**：优先使用 **`ContentMeta.repost_count`**；无 meta 时使用批量 `repost_counts`。

**已接入批量 context 的典型路径**（包括但不限于）：帖子列表、资产相关帖子、全局搜索中的帖子、管理端帖子列表、Dashboard 热门帖、行情模块 `asset_contents`、关注信息流中的帖子、用户收藏列表等。

### 4.3 帖子详情 GET：`select_related('author')`

- **`content_detail`** 查询增加对 **`author`** 的 `select_related`，避免在序列化作者信息时额外命中数据库。

### 4.4 收藏列表：链式 `select_related` / `prefetch_related`

- 用户收藏接口对 `Favorite → content → …` 增加 **`content__author`** 及帖子展示所需的 M2M/附件/meta/投票等预取（以实际代码为准），与卡片序列化字段一致。

### 4.5 评论列表：回复预览批量 + 评论点赞批量

- **`prefetch_reply_previews_for_comments`**：对当前页顶级评论批量加载「每帖前若干条回复」，避免在 `get_replies` 中对每条父评论重复查询。
- **`build_comment_like_context`**：对当前页涉及的评论 ID（含预览子回复）批量查询 **`Like`**（`target_type='COMMENT'`），写入 **`liked_comment_ids`**，`CommentSerializer.get_isLiked` 优先集合判断。
- **`post_comments` GET**、**`comment_replies`**、**详情内嵌评论块**等路径按场景传入上述 context。

### 4.6 行情榜单逻辑复用

- 抽取 [`background/market_data/rankings.py`](../background/market_data/rankings.py)：`get_cached_rankings_payload` 与 **`GET /api/market/rankings/`** 共用缓存键与计算逻辑，便于 Dashboard 等服务端聚合复用，避免重复实现。

### 4.7 页面级聚合接口扩展

| 接口 | 说明 |
|------|------|
| **`GET /api/dashboard/overview/`** | 支持 Query **`include`**（逗号分隔），例如 `rankings,gainers,hotAssets,active,notifUnread`。可在同一响应中附带涨幅榜、活跃榜、未读通知数等（登录用户），缓存键随 `include` 变化（实现中版本如 **`v3`**）。 |
| **`GET /api/users/{id}/overview/`** | 用户主页首屏聚合：**公开资料** + **近期公开帖子（卡片）** + **近期公开组合** + **关注统计**，减少前端对同一用户并行多次列表请求。 |

### 4.8 前端字段约定（与后端协同）

- 前端 `Post` 类型同时支持 **`excerpt`** 与 **`content`**；列表与卡片展示使用 **`post.excerpt || post.content`**，详情页仍以全文为主。

## 5. 论文撰写可参考的表述角度

以下内容可按学校格式改写后用于「系统优化」「非功能需求」「接口设计」等小节：

1. **列表与详情分离的响应模型**：列表接口以摘要字段为主，降低网络传输与序列化开销；详情接口承担全文与完整关联，符合「读多写少、读场景分层」的常见实践。
2. **批量预取用户互动状态以降低 N+1**：在服务端对当前页主键集合一次性查询点赞/收藏/转发计数，通过序列化 context 注入，避免在循环中访问 ORM。
3. **适度聚合（BFF 思路）**：在单一端点（如 Dashboard、用户 overview）组合多块只读数据，减少浏览器与服务器之间的往返次数，与「纯粹资源型 REST」形成互补而非替代。
4. **可观测性**：通过接口耗时日志与可选 SQL 分析工具，对关键路径做优化前后对比，支撑非功能需求验收描述。

## 6. 验证与回归建议

1. **环境变量**：`DJANGO_API_TIMING_LOG=true`，在 `django.log` 中检索 `api_timing`、`duration_ms`（详见 [`background/PERF_NOTES.md`](../background/PERF_NOTES.md)）。
2. **建议重点观察的 URL**（优化前后对比 SQL 次数与响应体大小）：
   - `GET /api/posts/`
   - `GET /api/posts/{id}/`
   - `GET /api/posts/{id}/comments/`
   - `GET /api/assets/{id}/posts/`、`GET /api/assets/{id}/contents/`
   - `GET /api/dashboard/overview/`（含与不含 `include`）
   - `GET /api/users/{id}/overview/`
3. **预期现象**：列表不再对每条帖子单独 `exists()` 点赞/收藏；列表 JSON 以 **`excerpt`** 为主，体积应明显小于带全文的旧列表响应。
