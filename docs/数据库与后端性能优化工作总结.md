# InvestHub 数据库与后端性能优化工作总结

> **文档用途**：汇总 **MySQL/Django ORM 数据库层** 优化（索引、全文检索、冗余计数、冷热数据策略）与 **接口层** 优化（列表瘦身、批量查询、聚合接口），便于毕业论文「数据库设计 / 系统实现 / 性能优化 / 非功能需求」等章节撰写，以及工作记录与后续迭代对照。  
> **适用范围**：Django + DRF + MySQL 8.x；与 [`docs/前端性能与优化工作总结.md`](./前端性能与优化工作总结.md) 互补（前端侧重构建与首屏，本文侧重数据层与 API）。

---

## 1. 总览：优化两条主线

| 主线 | 目标 | 典型手段 |
|------|------|----------|
| **数据库层** | 降低热点表扫描与排序代价、避免 `%keyword%` 全表模糊查询、用冗余字段减少列表 `COUNT(*)` | 联合索引、FULLTEXT、字段前缀匹配、反范式计数、归档策略 |
| **接口与 ORM 层** | 降低 SQL 次数与响应体积 | 列表/详情分离、`select_related` / `prefetch_related`、批量互动状态、Dashboard / Overview 聚合 |

两条线相互配合：例如帖子列表既依赖 **`content(status, created_at)`** 等索引，也依赖 **`ContentCardSerializer` + `build_post_card_context`** 避免 N+1。

## 2. 数据库层专项

### 2.1 背景与热点表

投资社区系统中，**内容、评论、内容–标的关联、组合、持仓、行情快照、K 线** 等表容易成为访问热点；查询多围绕 **用户、内容、标的、时间排序** 展开。优化前需对齐「最常见查询」与「索引最左前缀」。

### 2.2 索引：已落地的联合索引

以下索引在对应 Django 模型的 `Meta.indexes` 中声明，并由迁移创建（名称以实际迁移为准）。

| 表 / 模型 | 索引（逻辑） | 业务含义 |
|-----------|----------------|----------|
| `content_asset`（`ContentAsset`） | `(asset_id, created_at DESC)` | 标的讨论区：按标的筛帖子并随时间排序时，减少在关联表上的排序/回表代价 |
| `favorite`（`Favorite`） | `(user_id, created_at DESC)` | 「我的收藏」按收藏时间倒序列表 |
| `portfolio_subscription`（`PortfolioSubscription`） | `(user_id, created_at DESC)`、`(portfolio_id, created_at DESC)` | 用户订阅列表、某组合订阅者列表按时间 |
| `portfolio_comment`（`PortfolioComment`） | `(portfolio_id, created_at)`、`(parent_id, created_at)` | 组合下评论与楼中楼回复 |

**说明**：`market_data` 中 `AssetQuoteSnapshot`、`AssetKline` 等表在专项前已具备与「标的 + 时间 / 周期」匹配的索引设计，本轮未重复改动；详见模型与既有迁移。

**未在本阶段强上的索引**（计划中有意克制）：如超宽联合索引 `(status, -like_count, -comment_count, -created_at)`，需以慢查询与 `EXPLAIN` 证明 `filesort` 成瓶颈后再考虑。

### 2.3 搜索策略：帖子 FULLTEXT + 资产前缀匹配

- **帖子关键词**（列表参数 `q`、`GET /api/search/` 中的帖子）：在 **MySQL** 上使用 `MATCH(title, body) AGAINST (... IN NATURAL LANGUAGE MODE)`，依赖迁移 **`content.0010`** 创建的 **`FULLTEXT INDEX ft_content_title_body (title, body)`**。非 MySQL 环境（如本地 SQLite）回退为 `title`/`body` 的 `icontains`。
- **资产关键词**：对 **`code`** 使用 **`istartswith`**（前缀匹配，易走索引），对 **`name` / `industry`** 仍可用 `icontains` 作补充。
- **全局搜索**侧继续沿用较短 **TTL 缓存**（如 `GLOBAL_SEARCH_CACHE_TTL`），降低重复检索压力。
- **中文全文**：若自然语言分词效果不足，可在运维阶段评估 **ngram 解析器** 重建 FULLTEXT（需 DBA 评估词长与存储）。

实现入口：[`background/content/search_helpers.py`](../background/content/search_helpers.py)（`filter_posts_by_keyword`、`filter_assets_by_keyword`），由 [`content/views.py`](../background/content/views.py) 中帖子列表、资产列表、`global_search` 等调用。

### 2.4 反范式统计字段

| 字段 | 模型 | 维护方式 |
|------|------|----------|
| `like_count` / `comment_count` / `view_count` | `Content` | 既有：在点赞/评论等视图中用 `F()` 增量更新 |
| **`favorite_count`** | **`Content`** | **新增**：`POST/DELETE` 收藏接口中对 `Favorite` 创建/删除时同步 `F()` / `Greatest`；迁移 **`0010`** 按 `favorite` 表 **回填**历史数据 |
| **`subscription_count`** | **`Portfolio`** | **新增**：订阅/取消订阅接口中 `F()` 维护；迁移 **`portfolios/0007`** **回填** |
| `like_count` | `Portfolio` | 既有 |

列表展示 **收藏数、订阅数** 时可直读字段，避免在热点列表上对大表频繁 `annotate(Count(...))`（组合列表中原有的「组合收藏数」仍可能通过 `annotate` 与 `PortfolioFavorite` 关联，与「订阅数」字段语义不同，需注意区分）。

### 2.5 收藏列表语义与排序

用户收藏接口对 `Favorite` 查询显式 **`order_by('-created_at')`**，保证「最近收藏在前」，与 `(user, -created_at)` 索引一致。涉及实现：[`content/views.py`](../background/content/views.py)、[`accounts/views.py`](../background/accounts/views.py) 中用户收藏列表。

### 2.6 冷热数据与归档（运维向）

| 数据 | 策略说明 |
|------|----------|
| `asset_quote_snapshot` | 模型注释建议短期保留；实现见 `market_data.tasks.cleanup_old_snapshots(days=7)`，建议定时任务执行 |
| `asset_kline` | 按业务保留最近 N 根/区间；历史可迁冷表或对象存储；可与 `DQ_CHECK` 等任务结合 |
| `notification` | 大量历史可按期归档或清理，避免主表无限增长（需单独迁移/任务） |

更细的运维备忘见 [`background/PERF_NOTES.md`](../background/PERF_NOTES.md)。

### 2.7 验证：EXPLAIN 与慢 SQL

- 管理命令：**`python manage.py db_explain_hot_paths`**（[`background/content/management/commands/db_explain_hot_paths.py`](../background/content/management/commands/db_explain_hot_paths.py)），对帖子流、标的讨论区、收藏排序、帖子/资产关键词等 queryset 输出 **`EXPLAIN`**，用于核对 `key`、`rows`、`Extra`。
- 接口耗时：环境变量 **`DJANGO_API_TIMING_LOG`**，在 `django.log` 中检索 `api_timing` / `duration_ms`。
- 建议重点对照的 URL 与 [`background/PERF_NOTES.md`](../background/PERF_NOTES.md) 中一致，并增加对 **`GET /api/search/`**、带 **`q`** 的帖子/资产列表的关注。

## 3. 接口与 ORM 层专项（与历史「后端性能总结」一致）

以下小节对应原 [`docs/后端性能与优化工作总结.md`](./后端性能与优化工作总结.md) 中的接口与查询优化内容，便于单文档阅读；若需区分「仅接口」与「全栈」版本，可仍以该文件为精简引用版。

### 3.1 工程背景（接口侧）

- 同一页面多次 HTTP、ORM **N+1**、列表返回**正文全文**等，会带来延迟与带宽压力。
- 项目以「**列表与详情分离**、**批量预取互动状态**、**适度页面级聚合**」为主线，并与前端 **`excerpt` / `content`** 字段约定对齐。

### 3.2 技术栈与观测手段

| 层级 | 选型 |
|------|------|
| Web | Django + DRF |
| 数据库 | MySQL 8.x，Django ORM |
| 缓存 | Django 缓存（Dashboard、榜单、搜索等） |
| 耗时日志 | `invest_backend/perf_timing.py`，`DJANGO_API_TIMING_LOG` |
| 可选 | Django Debug Toolbar / django-silk |

### 3.3 既有后端能力（专项前基线）

- **`GET /api/dashboard/overview/`**：聚合热门帖子、组合、`marketSeries` 等；缓存键区分用户；`select_related` / `prefetch_related`。
- **行情榜单**：`GET /api/market/rankings/` 与 `AssetQuoteSnapshot`、缓存、索引设计。
- **请求耗时**：部分接口 `@timed_api` 装饰。

### 3.4 列表与详情分离：`ContentCardSerializer`

- 列表/卡片：主文为 **`excerpt`**（正文截断，约 320 字），不返回全文 **`content`**。
- 详情：仍返回全文（映射 `body`）。
- 标的/板块：`AssetCardSerializer`、`BoardCardSerializer` 仅列表所需字段；投票用 `PollCardSerializer` 摘要。

### 3.5 批量互动状态与转发数

- [`background/content/post_list_helpers.py`](../background/content/post_list_helpers.py)：`build_post_card_context`、`build_comment_like_context`、`prefetch_reply_previews_for_comments`。
- `PostInteractionMixin`：优先使用 context 中集合，避免逐条 `exists()` / `count()`。
- 转发数：优先 **`ContentMeta.repost_count`**，否则用批量 `repost_counts`。

### 3.6 其他接口层要点

- 帖子详情 **`select_related('author')`**。
- 收藏列表链式预取 `Favorite → content → …`。
- 行情榜单逻辑复用 [`background/market_data/rankings.py`](../background/market_data/rankings.py)。
- **`GET /api/dashboard/overview/?include=...`**、**`GET /api/users/{id}/overview/`** 等页面级聚合，减少前端并发请求。

### 3.7 前端字段约定

- 列表：`post.excerpt || post.content`；详情以全文为主。
- 数据库专项后，帖子卡片可增加 **`favoriteCount`**（后端字段 `favorite_count`）；组合列表可增加 **`subscriptionCount`**，类型定义见 `frontend/src/types/index.ts`。

## 4. 论文撰写可参考的表述角度

1. **数据库**：热点表联合索引与查询模式对齐；全文检索与模糊查询分离；适度反范式降低聚合开销；冷热数据与归档保证主表可维护性。
2. **接口与 ORM**：列表/详情分离；批量预取互动状态消除 N+1；BFF 式聚合减少往返。
3. **可观测性**：`EXPLAIN`、耗时日志、优化前后对比，支撑非功能需求验收。

## 5. 验证与回归建议（合并清单）

1. `DJANGO_API_TIMING_LOG=true`，检索 `django.log`。
2. `python manage.py db_explain_hot_paths`（MySQL 环境优先）。
3. 重点 URL：`GET /api/posts/`（含 `sort=hot`、`q`）、`GET /api/assets/{id}/posts/`、`GET /api/search/`、`GET /api/users/me/favorites/`、`GET /api/dashboard/overview/`、`GET /api/users/{id}/overview/` 等。
4. 预期：列表无逐条点赞/收藏 `exists()`；列表 JSON 以 **`excerpt`** 为主；带 **`q`** 时帖子在 MySQL 上可走 **FULLTEXT**（需已执行迁移 **0010**）。
