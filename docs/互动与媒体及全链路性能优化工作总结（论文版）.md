# InvestHub 互动与媒体及全链路性能优化工作总结（论文版）

> **文档用途**：将「评论、点赞、收藏、关注」高频交互优化与「文件/媒体资源」优化，以及既有的数据库、后端、缓存、前端性能工作进行统一归档，便于后续论文撰写、答辩展示与研发留档。  
> **覆盖范围**：`background/`（Django + DRF + MySQL + 可选 Redis/Celery）与 `frontend/`（Vue3 + Vite + Element Plus）。

---

## 1. 本轮优化目标与结论

### 1.1 目标

1. **高频交互写路径短事务化**：点赞、评论、关注等写请求以“主写入 + 最小计数更新”为核心。  
2. **评论大树分页优化**：一级评论首屏分页固定，二级回复按需按页累加。  
3. **媒体资源闭环**：上传限制、缩略图产出、列表小图优先、Nginx `/media/` 直出。  
4. **兼容可落地**：在未启用 Celery worker 的情况下，仍保证业务正确性。

### 1.2 结论

- 后端写路径已收敛：核心事务只做必要写入和计数字段更新，通知/积分等衍生逻辑通过 `transaction.on_commit` + 任务延后执行。  
- 评论加载策略完成：`GET /api/posts/{id}/comments/` 统一返回分页结构，前端新增“加载更多评论/回复”。  
- 媒体能力补齐：上传大小与像素上限校验 + `thumb` 字段与 `thumbUrl` 输出 + 列表页优先小图。  
- 部署侧补齐：Nginx 配置已给出 `/media/` 直出示例与上传限制对齐参数。

## 2. 本轮核心改造（互动与媒体）

### 2.1 高频交互：短事务 + 异步衍生逻辑

#### 2.1.1 任务抽象

新增：`background/notifications/community_tasks.py`

- 统一封装互动副作用任务：点赞事件、评论事件、关注事件、提及事件、积分发放、关注流写入。  
- 提供 `safe_task_delay(...)`：
  - 有 Celery `.delay` 时异步执行；
  - 无 Celery 时退化为同步调用；
  - 仍配合 `transaction.on_commit`，保证主事务先提交。

#### 2.1.2 内容侧写路径

关键文件：`background/content/views.py`

- 评论创建：`transaction.atomic()` 内只做评论写入与 `comment_count` 原子更新；积分与评论事件移到 `on_commit`。  
- 点赞（帖子/评论）：`atomic + get_or_create + F()` 计数更新，点赞通知移到 `on_commit`。  
- 发帖发布相关：积分和关注流写入延后到任务侧。  
- `@提及`：主请求内落库 `Mention`，通知事件在提交后执行。

#### 2.1.3 关注关系计数原子化

关键文件：`background/accounts/views.py`

- 关注/取关计数改为数据库原子表达式：
  - 关注：`F('...') + 1`
  - 取关：`Greatest(F('...') - 1, 0)`
- 避免“读-改-写”并发覆盖问题。  
- 关注通知改为 `on_commit + publish_follow_created_task`。

#### 2.1.4 Celery 发现

关键文件：`background/invest_backend/celery.py`

- 注册 `notifications.community_tasks`，确保 worker 可发现并执行任务。

### 2.2 评论分页与大评论树优化

#### 2.2.1 后端统一分页响应

关键文件：`background/content/views.py`

`GET /api/posts/{id}/comments/` 返回：

```json
{
  "items": [...],
  "page": 1,
  "pageSize": 20,
  "total": 123
}
```

- 默认 `page=1&pageSize=20`。  
- 保留 reply preview（每条顶评预览少量回复）以降低首屏负载。

#### 2.2.2 前端交互改造

关键文件：
- `frontend/src/api/posts.ts`
- `frontend/src/views/PostDetail.vue`

改造点：

- 一级评论首屏固定请求 `page=1&pageSize=20`。  
- 新增“加载更多评论”。  
- 二级回复从“单次大包（50）”改为分页累加（`REPLY_PAGE_SIZE=15`）。  
- 展开/收起与“加载更多回复”联动，减少大帖一次性请求量。

### 2.3 文件与媒体资源优化

#### 2.3.1 上传限制与校验

关键文件：
- `background/content/thumbnail_utils.py`（新增）
- `background/content/views.py`

策略：

- 文件大小上限：
  - 内容附件：12MB
  - 评论附件：5MB
- 图片像素上限：单边最大 8000px。  
- 非法文件、超限文件在上传接口直接返回 400。

#### 2.3.2 缩略图生成与存储

关键文件：
- `background/content/models.py`
- `background/content/migrations/0011_attachment_thumb_fields.py`
- `background/content/serializers.py`

落地内容：

- `ContentAttachment` 与 `CommentAttachment` 新增 `thumb` 字段。  
- 图片上传后自动生成缩略图（JPEG，约 400px 级别）。  
- 序列化输出 `thumbUrl`，详情可继续使用原图 `fileUrl`。

#### 2.3.3 列表页优先小图

关键文件：
- `background/content/serializers.py`（`ContentCardSerializer.thumbUrl`）
- `frontend/src/views/Community.vue`
- `frontend/src/views/Dashboard.vue`
- `frontend/src/views/Search.vue`
- `frontend/src/types/index.ts`

策略：

- 帖子卡片优先使用 `thumbUrl`，并启用 `loading="lazy"`。  
- 降低列表首屏图片流量与渲染压力。

#### 2.3.4 Nginx 媒体直出

关键文件：`docs/nginx-frontend.example.conf`

新增/强化：

- `location /media/ { alias ... }` 直出 Django `MEDIA_ROOT`。  
- `expires` 与 `Cache-Control` 配置示例。  
- `/api/` 增加 `client_max_body_size 15m` 与后端上传策略对齐。

## 3. 与既有优化工作的关系（全链路视角）

本轮改造并非孤立，而是与既有优化形成闭环：

1. **数据库与后端优化**（`docs/数据库与后端性能优化工作总结.md`）  
   - 索引、FULLTEXT、冗余计数、列表/详情分离、批量上下文去 N+1。  
2. **缓存层优化**（`docs/缓存层性能优化工作总结.md`）  
   - Django Cache/Redis、行情 L1/L2/L3、浏览量缓冲回写。  
3. **前端优化**（`docs/前端性能与优化工作总结.md`）  
   - 路由与重型组件懒加载、空闲调度、构建分包与压缩。  
4. **本轮互动与媒体优化**（本文第 2 节）  
   - 高频写路径、评论树分页、上传与缩略图、媒体直出。

> 论文可表述为：系统从“数据库-接口-缓存-前端-媒体资源分发”五个层面建立了端到端性能优化体系。

## 4. 回归测试与验收建议

参考 `background/PERF_NOTES.md`，建议至少覆盖：

1. 点赞/取消赞（帖子与评论）响应时间与正确性。  
2. 发表评论/回复后计数正确、事件与积分在提交后执行。  
3. 关注/取关并发下计数不丢失。  
4. 评论分页与回复分页不重复、不漏数据。  
5. 上传超限文件/超像素图片返回 400。  
6. 列表页优先小图、详情页可访问原图。  
7. 生产环境 `/media/` 由 Nginx 直出，不经 Django 透传大文件。

## 5. 论文写作可直接复用的亮点

1. **短事务与最终一致性结合**：主事务最小化，衍生逻辑异步化。  
2. **高并发计数正确性**：`F()` 与 `Greatest()` 防止并发覆盖。  
3. **评论大树按需加载**：分页 + 预览策略兼顾体验与性能。  
4. **媒体资源工程化治理**：上传校验、缩略图、媒体直出全链路闭环。  
5. **全栈协同优化**：数据库、缓存、接口、前端、部署策略协同。
