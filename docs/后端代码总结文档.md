# 《股票基金投资社区系统后端代码总结文档》

## 1. 后端整体定位

### 1.1 后端在整个系统中的作用

本项目后端位于 `background/`，采用 `Django + Django REST Framework + MySQL + JWT + Redis（可选） + Celery（可选）` 技术栈，承担系统的核心业务编排、数据持久化、权限控制、第三方行情接入、通知分发、治理审核与统计分析等职责。

后端并不是一个“纯 CRUD 服务”，而是整个投资社区系统的业务中台，主要负责：

- 为前端主应用提供 REST API。
- 对用户、内容、组合、行情、举报、通知、群组、私信等领域进行统一建模。
- 执行认证鉴权、对象权限判断、用户状态校验、审核治理逻辑。
- 对接 Finnhub、Tushare 等第三方数据源。
- 通过缓存、定时任务、SSE 等方式提供性能与实时性能力。

### 1.2 后端主要承载的业务能力

当前后端主要覆盖以下业务域：

- 账号与身份：注册、登录、JWT、验证码、OAuth、实名认证、专业认证、风险测评、投资偏好。
- 社区内容：帖子发布、详情、评论、点赞、收藏、转发、投票、附件、搜索、板块、资产讨论区。
- 投资组合：组合创建、详情、收益指标、评论、收藏、订阅、持仓与收益历史。
- 行情数据：资产行情、K 线、分时、批量行情、行情榜单、数据同步任务监控。
- 通知系统：站内通知列表、已读、SSE 实时通知。
- 举报与治理：举报、告警、审核队列、审核规则、统计分析。
- 社交补充：关注关系、关注流、私信会话、群组与群资料。

### 1.3 后端与前端、数据库、第三方服务的关系

- 与前端关系：前端通过 `frontend/src/api/*.ts` 调用后端 REST 接口，接口风格以 JSON 为主，列表通常使用 `items/page/pageSize/total`。
- 与数据库关系：后端以 Django ORM 为主访问 MySQL，核心业务模型集中在各 app 的 `models.py`。
- 与缓存关系：通过 Django Cache 抽象接 Redis 或 LocMem，主要用于行情、榜单、板块树、搜索、管理台统计等热点只读场景。
- 与第三方服务关系：
  - `market_data/finnhub_service.py`：美股/港股行情与 K 线。
  - `market_data/tushare_service.py`：A 股日线、部分市场数据同步。
  - `accounts/oauth/*`：微信/微博 OAuth。
  - 邮件/SMS：验证码发送。

### 1.4 后端与哪些模块关联最紧密

耦合最紧密的三个中心模块是：

- `accounts`：自定义用户模型是全站主锚点，几乎所有业务都依赖 `accounts.User`。
- `content`：`Asset` 与 `Content` 是内容域和行情/组合域之间的桥梁。
- `market_data`：行情读取、K 线同步、组合收益计算、首页榜单等能力都依赖该模块。

## 2. 后端功能总览

### 2.1 当前后端已实现的核心功能

已实现的核心功能包括：

- 用户注册、登录、JWT 刷新、验证码发送/校验、第三方 OAuth 登录与绑定。
- 用户资料、隐私设置、关注/特别关注、成就、关注流。
- KYC、专业认证、风险问卷、投资偏好。
- 帖子发布、编辑、删除、评论、回复、点赞、收藏、转发、投票、附件上传下载。
- 资产库、板块树、资产讨论区、搜索、Dashboard 概览。
- 组合创建、公开/私有访问控制、评论、收藏、订阅、持仓、收益表现、收益历史。
- 行情查询、K 线、分时、批量报价、SSE 行情流、榜单、数据任务触发与监控。
- 通知列表、标记已读、SSE 实时通知。
- 举报提交、管理员处理、审核队列、规则命中、告警、运营统计分析。
- 私信会话、消息列表、消息已读、图片附件。
- 群组创建、入群申请、邀请、成员角色、群讨论、群资料。

### 2.2 各功能模块之间的关系

- `accounts` 是身份基础模块。
- `content` 是社区主业务模块。
- `portfolios` 是结构化内容模块，与 `content.Asset`、`market_data` 强关联。
- `market_data` 是行情基础能力模块，为 `content`、`portfolios`、首页数据提供支撑。
- `notifications` 是横切模块，消费点赞、评论、关注、审核等业务事件。
- `reports` 是治理与分析模块，连接 `content`、`accounts`。
- `messages`、`groups` 是社交补充模块。

### 2.3 主业务流程与支撑能力划分

主业务流程：

- 用户认证与身份建立。
- 内容生产与互动。
- 组合分享与收益展示。
- 行情浏览与资产讨论。
- 举报与审核治理。

支撑能力：

- JWT、权限控制、验证码、OAuth。
- 缓存、日志、性能打点、定时任务。
- 通知事件总线与异步副作用。
- 私信、群组等增强社交能力。

## 3. 后端目录结构分析

### 3.1 核心目录清单

#### 项目根目录下的重要目录及职责

- `background/manage.py`：Django 管理命令入口。
- `background/invest_backend/`：项目级配置目录，存放 settings、总路由、WSGI/ASGI、Celery、全局权限与性能打点工具。
- `background/accounts/`：用户、认证、社交关系、KYC、风险问卷、用户治理。
- `background/content/`：帖子、评论、板块、资产、收藏点赞转发、附件、搜索。
- `background/portfolios/`：投资组合、持仓、收益历史、评论、订阅、收藏。
- `background/market_data/`：行情、K 线、同步任务、第三方行情接入。
- `background/notifications/`：通知实体、事件分发、实时流。
- `background/reports/`：举报、审核、告警、分析统计。
- `background/messages/`：私信会话与消息。
- `background/groups/`：群组、成员、邀请、群讨论、群资料。
- `background/*/management/commands/`：批处理、重建统计、导入数据、修复数据等脚本。

#### apps/modules 目录作用

项目采用 Django app 粒度拆分领域，每个 app 大多包含：

- `models.py`：领域模型。
- `serializers.py`：请求校验与响应组装。
- `views.py`：主要业务入口，包含 API 逻辑。
- `urls.py`：当前 app 对外路由。
- `management/commands/`：管理命令。
- 部分 app 还包含 `tasks.py`、`service.py`、`events.py`、`helpers.py`。

#### config/settings 目录作用

- `invest_backend/settings.py`：全局配置中心，包含数据库、JWT、DRF、缓存、日志、Celery、第三方服务参数。
- `invest_backend/urls.py`：总路由入口。
- `invest_backend/permissions.py`：项目级角色权限类。

#### urls/router 目录作用

- 总路由在 `invest_backend/urls.py`。
- 各 app 通过 `include()` 按模块接入。
- 认证与用户相关路由进一步拆成 `accounts/urls.py`、`accounts/user_urls.py`、`accounts/feed_urls.py`、`accounts/admin_urls.py`。

#### services 目录作用

项目没有严格统一的 `services/` 目录，但已有若干服务化模块：

- `accounts/feed_service.py`：关注流写入。
- `accounts/user_score_service.py`：积分与等级变更。
- `accounts/message_service.py`：验证码发送。
- `content/moderation_service.py`：内容审核辅助。
- `reports/analytics_service.py`：统计重建。
- `market_data/finnhub_service.py`、`tushare_service.py`：第三方行情接入。

#### models 目录作用

当前不是 `models/` 子目录式拆分，而是单个 app 下集中在一个 `models.py` 中。优点是查找快，缺点是随着模型增多后文件会变长。

#### serializers/schemas 目录作用

使用 DRF `serializers`，主要承担：

- 入参校验。
- 模型保存。
- 输出字段组装。
- 部分复杂派生字段计算。

当前没有额外 schema 层。

#### permissions/middleware/utils 目录作用

- `invest_backend/permissions.py`：角色权限类。
- `accounts/permissions.py`：认证等级权限类。
- 无自定义 Django middleware。
- utils/helper 分散于各 app，例如 `content/search_helpers.py`、`content/cache_utils.py`、`content/post_list_helpers.py`。

#### scripts/tasks/jobs 目录作用

- `market_data/tasks.py`：行情同步主逻辑。
- `market_data/celery_tasks.py`：Celery 任务包装。
- `notifications/community_tasks.py`：通知/积分/关注流副作用任务。
- `management/commands/`：导入、重建、同步、修复、快照回填。

### 3.2 核心文件清单

#### 主入口文件

- `background/manage.py`：Django 命令入口。
- `background/invest_backend/settings.py`：全局配置入口。
- `background/invest_backend/urls.py`：总路由入口。
- `background/invest_backend/wsgi.py`：WSGI 部署入口。
- `background/invest_backend/asgi.py`：ASGI 部署入口。
- `background/invest_backend/celery.py`：Celery 应用入口。

#### 高频依赖文件

- `background/accounts/models.py`：全站自定义用户模型。
- `background/content/models.py`：内容与资产主模型。
- `background/accounts/views.py`：认证、资料、关注、治理、关注流等多类接口集中。
- `background/content/views.py`：帖子、评论、搜索、板块、上传、管理端接口集中。
- `background/market_data/tasks.py`：行情同步核心逻辑。
- `background/portfolios/views.py`：组合与持仓计算主逻辑。
- `background/notifications/events.py`：通知事件总线。
- `background/reports/views.py`：举报、审核、统计分析入口。

#### 高风险文件

- `background/invest_backend/settings.py`
  - 影响全站认证、缓存、日志、数据库、第三方能力。
- `background/invest_backend/urls.py`
  - 影响所有 API 路由命中顺序。
- `background/accounts/views.py`
  - 体量大、职责杂、修改容易产生回归。
- `background/content/views.py`
  - 业务核心，且包含多类接口。
- `background/content/serializers.py`
  - 帖子、评论、资产、板块输出逻辑集中。
- `background/market_data/tasks.py`
  - 第三方行情拉取、缓存、同步、批量写库都在此集中。
- `background/portfolios/views.py`
  - 组合指标、收益历史、持仓计算复杂。
- `background/notifications/events.py`
  - 修改通知语义会影响全站用户触达。

## 4. 模块划分与架构分析

### 4.1 模块清单

#### 基础模块

- `accounts`：用户、认证、权限等级、关注关系、积分与行为统计。
- `market_data`：行情与数据同步基础能力。
- `notifications`：横向通知模块。

#### 主业务模块

- `content`：社区内容主域。
- `portfolios`：投资组合分享主域。
- `reports`：举报审核与运营分析域。

#### 补充业务模块

- `messages`：私信系统。
- `groups`：群组系统。

### 4.2 分层结构

当前项目整体偏向 Django/DRF 常见的 “Model + Serializer + View” 三层组织：

- View 层：API 入口、参数读取、权限判断、业务编排、响应返回。
- Serializer 层：字段校验、对象保存、输出序列化。
- Model 层：数据结构、约束、少量领域方法。
- Service/Helper 层：只在部分场景存在，尚未形成统一规范。

#### 每层职责现状

- `views.py`
  - 承担了较多业务逻辑。
  - 包含权限判断、事务控制、查询构造、事件投递、响应拼装。
- `serializers.py`
  - 既负责校验，也承担部分输出聚合与创建更新逻辑。
- `models.py`
  - 更多是数据结构定义，业务规则未明显下沉到 model 层。
- service/helper
  - 已有局部封装，但覆盖不均。

#### 当前职责混乱问题

存在明显的“重视图”倾向：

- `accounts/views.py` 同时承载认证、KYC、用户资料、关注、关注流、治理、积分管理。
- `content/views.py` 同时承载帖子、评论、点赞、收藏、上传、板块、搜索、后台审核入口。
- `portfolios/views.py` 承担了收益与绩效计算、序列化上下文构造、交互逻辑。
- `reports/views.py` 同时处理举报、审核队列、告警、分析看板。

也存在“序列化器承担过多业务逻辑”的现象：

- `content/serializers.py` 中帖子详情、列表、创建、评论等逻辑集中。
- `portfolios/serializers.py` 承担组合/持仓输入输出与部分组合资产处理。

### 4.3 架构特点

#### 当前风格

- 框架风格：Django MTV。
- API 风格：DRF + 偏 RESTful。
- 业务组织风格：以 app 为边界的领域拆分，辅以局部 service-oriented 封装。

#### 优点

- 领域划分清晰，按 app 定位成本较低。
- 资产、内容、用户模型是稳定的主轴。
- 行情同步、通知事件、统计重建已经开始服务化，具备进一步抽象基础。

#### 不足

- 模块间仍有较强跨 app import。
- 逻辑分层不统一，部分 view 非常厚。
- 权限风格不统一，既有 `permission_classes`，也有大量 `if request.user.role ...`。
- 响应格式靠手写约定，无全局约束。
- 手写分页较多，重复代码明显。

## 5. 路由系统分析

### 5.1 路由配置

#### 总路由入口文件

- `background/invest_backend/urls.py`

#### 路由挂载关系

- `/admin/` → Django Admin
- `/api/auth/` → `accounts.urls`
- `/api/users/` → `accounts.user_urls`
- `/api/feed/` → `accounts.feed_urls`
- `/api/admin/` → `accounts.admin_urls`
- `/api/` → `content.urls`
- `/api/` → `portfolios.urls`
- `/api/` → `notifications.urls`
- `/api/` → `reports.urls`
- `/api/` → `messages.urls`
- `/api/` → `groups.urls`
- `/api/` → `market_data.urls`

#### 路由前缀设计

- 认证独立前缀：`/api/auth/`
- 用户中心独立前缀：`/api/users/`
- 关注流独立前缀：`/api/feed/`
- 用户治理独立前缀：`/api/admin/`
- 其余业务共用 `/api/` 前缀，再按资源名区分。

#### URL 命名规范

整体偏 RESTful，但存在以下混合情况：

- 资源风格：`posts/`、`portfolios/`、`notifications/`
- 动作风格：`favorite/`、`subscribe/`、`read-all/`、`transfer-owner/`
- 管理风格：`admin/posts/<id>/status/`、`admin/moderation/queue/`

#### 嵌套路由、动态参数、版本化

- 存在大量嵌套路由，例如：
  - `/api/posts/<pk>/comments/`
  - `/api/portfolios/<pk>/comments/`
  - `/api/groups/<group_id>/members/`
  - `/api/assets/<pk>/quote/`
- 动态参数使用较多，主要是 `<int:pk>`、`<int:user_id>`、`<int:group_id>`。
- 未见显式版本化路由，如 `/api/v1/`。

### 5.2 路由组织方式

#### 优点

- 路由已按业务模块拆分，定位总体清晰。
- 认证、用户、管理员接口拆分优于全部堆在单个 `urls.py`。
- 行情接口单独归于 `market_data/urls.py`，后续扩展方便。

#### 不统一点

- `/api/` 下挂多个 app，需依赖路径字符串避免冲突。
- 一部分接口以资源为中心，一部分接口以动作为中心。
- 某些路径包含兼容性写法，如 `content/urls.py` 同时保留 `comments/` 和 `comments` 两种版本。

### 5.3 路由修改风险

#### 修改总路由的影响

- 会影响所有 API 前缀命中。
- `include()` 顺序会影响重复路径的实际生效结果。

#### 已确认的高风险路由问题

- `accounts/user_urls.py` 定义 `/api/users/me/reports/`
- `reports/urls.py` 定义 `/api/users/me/reports/`

由于根路由中 `/api/users/` 在 `/api/` 之前加载，实际更容易命中 `accounts.user_urls`。这意味着：

- `reports.views.UserReportsView` 可能处于“重复实现但默认不生效”状态。
- 后续如果修改举报列表接口，必须同时检查 `accounts` 和 `reports` 两处实现。

#### 可能被前端强依赖的 URL

高概率强依赖的接口包括：

- `/api/auth/login/`
- `/api/auth/refresh/`
- `/api/users/me/`
- `/api/posts/`
- `/api/posts/<id>/`
- `/api/assets/<id>/quote/`
- `/api/assets/<id>/kline/`
- `/api/portfolios/`
- `/api/notifications/`
- `/api/notifications/stream/`

## 6. 接口规范分析

### 6.1 接口风格

项目总体采用 REST 风格，但不是严格纯 REST。

#### 请求方法使用

- `GET`：列表、详情、状态查询、统计。
- `POST`：创建、动作型操作（登录、点赞、收藏、订阅、标记已读、触发任务）。
- `PATCH`：部分更新、状态流转。
- `DELETE`：取消收藏、取消点赞、删除资源、退出群组等。

整体上方法使用基本合理，但有两类特征：

- 行为动作较多，导致 `POST /xxx/action/` 风格很常见。
- 某些删除并非物理删除，而是状态位更新，例如帖子删除实际变更为 `TAKEN_DOWN`。

### 6.2 返回结构规范

#### 成功返回格式

多数接口采用以下风格：

```json
{
  "code": 0,
  "data": {}
}
```

或：

```json
{
  "code": 0,
  "message": "操作成功"
}
```

#### 失败返回格式

常见失败结构：

```json
{
  "code": 4001,
  "message": "参数错误/创建失败/登录失败",
  "errors": {}
}
```

也会出现：

- `4010`：需要登录
- `4030`：无权限/用户状态不允许
- `4040`：资源不存在/未找到
- `4090`：状态冲突，如重复点赞、重复收藏、重复申请

#### 分页返回格式

大量列表接口采用统一的手写结构：

```json
{
  "code": 0,
  "data": {
    "items": [],
    "page": 1,
    "pageSize": 20,
    "total": 0
  }
}
```

#### 列表与详情差异

- 列表：通常返回轻量卡片字段，配合分页。
- 详情：返回更完整的模型信息、互动状态、关联对象。

#### 当前规范问题

- 没有全局响应封装器。
- 没有统一异常处理器兜底输出标准结构。

### 6.4 接口设计问题与建议

#### 已确认问题

- 接口返回结构依靠手写，缺少统一 ResponseBuilder。
- 重复接口已存在：`/api/users/me/reports/` 在 `accounts` 与 `reports` 各有实现。
- 路由存在兼容冗余：`/api/posts/<id>/comments/` 与不带尾斜杠版本同时存在。
- 部分接口命名偏动作化，资源语义不完全统一。
- 权限控制风格不统一，可能导致相同角色策略在不同模块表现不一致。

#### 建议

- 增加统一响应封装与异常处理器。
- 提取统一分页基类。
- 消除重复接口，明确唯一归属模块。
- 为动作类接口补充更清晰的领域命名规范。

## 7. 认证与权限控制分析

### 7.1 认证机制

#### 使用方式

- 认证方式：JWT。
- 核心配置：`settings.py -> REST_FRAMEWORK.DEFAULT_AUTHENTICATION_CLASSES`
- 使用库：`rest_framework_simplejwt`

#### 登录态生成、校验、续期、销毁

- 生成：`accounts/views.py -> get_tokens_for_user()` 使用 `RefreshToken.for_user(user)` 生成 `refresh` 与 `access`。
- 校验：DRF 默认走 `JWTAuthentication`。
- 续期：`/api/auth/refresh/` 通过 `TokenRefreshSerializer` 刷新。
- 销毁：`/api/auth/logout/` 当前仅返回“登出成功”，未真正做 refresh token 黑名单处理，实际依赖前端删除 token。

#### token 传递规范

- 标准接口：`Authorization: Bearer <access_token>`
- 通知 SSE：`notifications_stream()` 允许通过 `?token=` 查询参数传 token，再手动注入 `HTTP_AUTHORIZATION`。

#### refresh token 机制

`SIMPLE_JWT` 配置如下：

- Access：1 小时
- Refresh：7 天
- `ROTATE_REFRESH_TOKENS = True`
- `BLACKLIST_AFTER_ROTATION = True`

但当前 `INSTALLED_APPS` 中未见 `rest_framework_simplejwt.token_blacklist`，因此：

- refresh 黑名单机制是否完整生效：`待确认`
- 当前实现与 `logout()` 的“仅前端清除 token”逻辑存在不一致

### 7.2 权限控制

#### 全局权限

- `REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES = IsAuthenticated`

这意味着除非视图明确写 `AllowAny`，否则接口默认需要登录。

#### 项目级权限类

- `invest_backend/permissions.py`
  - `IsModeratorOrAdmin`
  - `IsAdminOnly`

#### 模块级权限类

- `accounts/permissions.py`
  - `IsBasicVerified`
  - `IsRealNameVerified`
  - `IsProfessionalVerifiedAndRiskAssessed`

#### 当前角色体系

- 游客：未登录。
- 普通用户：`role='USER'`
- 审核员：`role='MODERATOR'`
- 管理员：`role='ADMIN'`

#### 权限不足返回

常见返回为：

- `4010`：未登录。
- `4030`：无权限、被禁言/封禁、当前状态不允许操作。

### 7.3 用户认证相关流程

#### 登录流程

前端请求 `POST /api/auth/login/`：

1. 路由命中 `accounts.urls -> login`
2. `UserLoginSerializer` 校验账号密码
3. `login()` 检查 `user.status`、`is_active`
4. 生成 `access + refresh`
5. 返回 `code=0` 与用户信息

异常流程：

- 序列化失败 → `4001`
- 用户被封禁/禁用 → `4030`

#### 注册流程

通用注册：

1. `register()` 使用 `UserRegistrationSerializer`
2. `serializer.save()` 创建用户
3. 生成 JWT
4. 返回用户信息 + token

邮箱/手机注册：

1. 校验注册表单
2. 校验验证码
3. `transaction.atomic()` 内创建用户并回写验证码记录状态
4. 返回 JWT 与用户信息

#### 获取当前用户信息流程

1. 请求 `/api/users/me/`
2. `manage_current_user` 根据 `request.user` 读取当前用户
3. `GET` 返回资料，`PATCH` 更新资料

#### 退出登录流程

1. 请求 `/api/auth/logout/`
2. 返回成功消息
3. 当前后端未落 token 黑名单
4. 主要由前端清理 token

#### token 过期处理

- access 过期后应由前端调用 `/api/auth/refresh/`
- refresh 过期后需要重新登录

#### 用户状态异常处理

- 登录时：`BANNED` 或 `is_active=False` 会被拒绝登录
- 发帖/评论/上传时：检查 `request.user.status in ['MUTED', 'BANNED']`
- 某些接口使用了直接 `if user.role...` / `if user.status...` 判断，而不是统一权限类

## 9. 数据库调用与数据访问方式分析

### 9.1 数据访问方式

#### ORM 还是原生 SQL

以 Django ORM 为主，少量使用：

- `queryset.extra()`：如 `content/search_helpers.py` 中的 MySQL FULLTEXT 搜索。
- `cursor.execute()`：主要出现在迁移、数据修复、管理命令。

#### CRUD 主要位于哪些层

- 查询：主要位于 `views.py`
- 写入：位于 `serializer.save()`、`views.py`、少量 service
- 更新：位于 `views.py`、`serializer.update()`、`queryset.update()`
- 删除：部分物理删除，部分状态位删除

#### 是否有 service/repository 封装

- 无统一 repository 层。
- service 封装是局部存在而非全局规范。

#### 是否有事务处理

有，常见方式：

- `transaction.atomic()`
- `transaction.on_commit()`

其中 `on_commit()` 的使用是当前代码一个值得保留的优点，用于保证通知、积分、关注流等副作用在主事务提交后再执行。

### 9.2 常见查询与写入流程

#### 列表查询

典型模式：

1. 在 `get_queryset()` 中构造 queryset
2. 使用 `select_related/prefetch_related`
3. 读取 query params 做筛选、排序
4. 手动分页
5. serializer 输出
6. 返回 `items/page/pageSize/total`

#### 详情查询

典型模式：

1. `get_object_or_404()` 加关联预取
2. 做访问权限判断
3. serializer 输出详情
4. 返回 `code=0,data=...`

#### 创建流程

典型模式：

1. 权限校验
2. serializer 入参校验
3. `serializer.save(...)`
4. 必要时用 `transaction.atomic()`
5. `transaction.on_commit()` 触发副作用
6. 详情序列化返回

#### 更新流程

典型模式：

1. 读取对象
2. 对象级权限校验
3. `partial=True` 调用 serializer
4. 根据状态变化触发额外逻辑
5. 返回最新对象

#### 删除流程

分两类：

- 逻辑删除/状态删除：如帖子改为 `TAKEN_DOWN`
- 物理删除：如部分组合、持仓、群资料等

#### 批量操作、缓存、异步任务

- 批量写入：`market_data/tasks.py` 中大量 `bulk_create`
- 缓存：行情、板块树、榜单、统计、搜索等
- 异步任务：Celery 可选，行情同步与通知副作用都支持异步化

### 9.3 数据访问风险

#### 已做的优化

- 热点查询大量使用 `select_related/prefetch_related`
- 行情同步采用分批 `bulk_create`
- 部分接口做短 TTL 缓存

#### 主要风险

- N+1 风险仍存在于后续新增 serializer 字段时
- 手写分页与查询逻辑分散，后续容易出现重复查询
- 多个 view 直接操作 ORM，缺少统一查询服务层
- 跨 app 查询较多，修改中心模型时影响面大
- 事务边界不完全统一，若后续新增副作用忘记 `on_commit`，容易引入时序问题

## 10. 后端业务流程分析

以下按典型链路说明。

### 10.1 用户登录流程

#### 正常流程

前端请求 `POST /api/auth/login/`

1. 路由：`invest_backend/urls.py` → `accounts/urls.py`
2. View：`accounts.views.login`
3. Serializer：`UserLoginSerializer`
4. 业务逻辑：
   - 校验账号密码
   - 校验用户状态是否封禁
   - 生成 JWT
5. 数据库：
   - 查询 `user`
6. 返回：
   - `code=0`
   - `data.access`
   - `data.refresh`
   - `data.user`

#### 参数错误流程

- serializer 校验失败 → `4001`

#### 权限不足流程

- 用户已封禁/禁用 → `4030`

#### 资源不存在流程

- 账号密码错误统一表现为校验失败，通常走 `4001`

#### 服务异常流程

- 未见统一异常封装，默认会回落到 DRF/Django 异常响应，`待确认`

### 10.2 发帖流程

#### 正常流程

前端请求 `POST /api/posts/`

1. 路由：`invest_backend/urls.py` → `content/urls.py`
2. View：`ContentListView.create`
3. 权限：
   - 必须登录
   - `user.status` 不能为 `MUTED/BANNED`
4. Serializer：`ContentCreateSerializer`
5. 业务逻辑：
   - 保存帖子
   - 提取 mention
   - 事务提交后异步发积分
   - 若状态为 `PUBLISHED`，事务提交后写入关注流
6. 数据库：
   - 写 `content`
   - 可能写 `content_asset`、`content_board`、`mention`
7. 返回：
   - `ContentDetailSerializer` 序列化的帖子详情

#### 参数错误流程

- serializer 校验失败 → `4001 + errors`

#### 权限不足流程

- 未登录 → `4010`
- 被禁言/封禁 → `4030`

#### 资源不存在流程

- 资产 ID、板块 ID 非法时通常在 serializer 校验阶段失败

#### 服务异常流程

- 副作用任务异常理论上不阻断主请求，因为通过 `safe_task_delay` + `on_commit`

### 10.3 帖子详情/编辑/删除流程

前端请求 `GET/PATCH/DELETE /api/posts/<id>/`

1. 路由：`content/urls.py`
2. View：`content_detail`
3. 数据查询：`Content.objects.select_related('author').prefetch_related(...)`
4. 逻辑分支：
   - `GET`：未发布内容仅作者或审核员/管理员可见
   - `PATCH`：仅作者或审核员/管理员可编辑
   - `DELETE`：仅作者或审核员/管理员可删除，实际把 `status` 改为 `TAKEN_DOWN`
5. 其他：
   - GET 时会记录浏览量，可能走 Redis 缓冲

### 10.4 关注流生成流程

#### 正常流程

触发点：

- 关注用户成功
- 发帖成功并发布
- 公开组合创建/公开化

链路：

1. 主业务写库成功
2. `transaction.on_commit()` 调用 `safe_task_delay(...)`
3. 进入 `notifications/community_tasks.py` 或直接调用 `accounts/feed_service.py`
4. `write_follow_feed_for_actor()` 遍历粉丝列表
5. 写 `follow_feed_item`
6. `/api/feed/following/` 读取 feed item，再拼装帖子卡片返回

#### 风险点

- 目前是按粉丝逐条 `get_or_create`，当大 V 用户粉丝量很大时可能成为性能瓶颈

### 10.5 行情读取流程

#### 单资产行情 `GET /api/assets/<id>/quote/`

1. 路由：`market_data/urls.py`
2. View：`asset_quote`
3. 业务逻辑：
   - 取 `Asset`
   - 调 `get_or_refresh_quote(asset)`
4. 数据流：
   - 先读 Django Cache
   - 再读 `asset_quote_snapshot`
   - 缺失时按市场路由第三方接口
   - 成功后回写缓存/数据库
5. 返回：标准 JSON 行情结构

#### K 线 `GET /api/assets/<id>/kline/`

1. 读取 query 参数：`interval/limit/from/to`
2. 查询 `AssetKline`
3. 返回升序 `items`
4. 不在请求中主动做第三方回补，仅提示管理员触发同步

#### 分时 `GET /api/assets/<id>/intraday/`

1. 先查分钟级 `AssetKline`
2. 没数据时按市场决定是否拉第三方分钟线
3. A 股分钟线因 Tushare 权限限制，当前以降级提示为主

### 10.6 举报处理流程

#### 正常流程

1. 用户请求 `POST /api/reports/`
2. `ReportCreateSerializer` 校验举报对象、原因等
3. 写 `report`
4. 返回举报 id

管理员处理：

1. 请求 `PATCH /api/admin/reports/<id>/`
2. `handle_report` 读取举报记录
3. 校验管理员角色
4. 根据 `status/result/actionTaken` 更新举报
5. 若目标为帖子：
   - `TAKE_DOWN`：修改 `content.status='TAKEN_DOWN'`
   - `QUEUE_REVIEW/REVIEW`：创建或复用 `moderation_queue_item`
6. 返回成功消息

#### 风险点

- 举报对象是多态 `target_type + target_id`，对象不存在或已删除时需要特别谨慎处理

- 修改缓存 TTL 会影响行情与首页刷新频率。
- 当前数据库账号密码写死在文件中，生产环境必须改为环境变量。

### 11.2 `background/invest_backend/urls.py`

#### 为什么关键

- 所有 API 都由此进入。
- `include` 顺序会决定重复路径谁先命中。

#### 修改注意事项

- 任何新增 app 或前缀变更都要先改这里。
- 改顺序前要检查是否存在重复路径。

### 11.3 `background/accounts/views.py`

#### 为什么关键

这是最重的入口文件之一，承载：

- 认证
- 用户资料
- 关注关系
- 关注流
- KYC
- 风险测评
- 用户治理

#### 它解决的问题

- 把账号与身份相关大部分 API 集中在一个模块内。

#### 依赖关系

- 依赖 `accounts/serializers.py`
- 跨 app 依赖 `content`、`portfolios`、`reports`、`notifications`

#### 修改注意事项

- 任何登录、关注、治理、用户状态字段变动都要重点回归此文件。
- 建议后续拆分成 `auth_views.py`、`profile_views.py`、`social_views.py`、`admin_views.py`。

### 11.4 `background/content/views.py`

#### 为什么关键

它是社区内容主链路的核心。

#### 主要职责

- 帖子列表与详情
- 发帖、删帖、改帖
- 评论与点赞收藏
- 板块与附件
- Dashboard 和搜索

#### 修改注意事项

- 影响前台内容流、详情页、评论区、后台审核与首页聚合。
- 必须关注用户状态校验、对象权限、计数字段、副作用任务。

### 11.5 `background/market_data/tasks.py`

#### 为什么关键

- 行情同步、缓存、第三方路由、任务日志、批量入库几乎都在这里。

#### 输入输出

- 输入：资产、市场、任务类型、第三方返回结果
- 输出：快照/K 线写库、DataJobLog、缓存更新

#### 修改注意事项

- 很容易牵动首页、资产详情、组合收益、榜单。
- 任何第三方接入变更都应优先在这里收敛，不要把行情逻辑分散到更多 view 中。

### 11.6 `background/notifications/events.py`

#### 为什么关键

- 这是通知中心的事件桥梁。
- 业务侧只管发布事件，通知侧统一消费。

## 12. 异常处理、日志与通用能力分析

### 12.1 异常处理

#### 当前情况

- 未发现统一的 DRF 自定义异常处理器配置。
- 多数业务错误通过 `Response({...}, status=...)` 手写返回。
- 未见统一错误码枚举中心。

#### 影响

- 接口风格依赖开发者习惯。
- 一旦出现未捕获异常，返回结构可能不一致。

### 12.2 日志处理

#### 当前情况

- `settings.py` 中配置 root logger + `investhub.api_timing`
- 输出到 console 与 `django.log`

#### 风险

- `django.log` 使用相对路径，实际落盘位置依赖进程启动目录。
- 没有明确的审计日志、请求日志、异常日志分层。

### 12.3 公共能力

#### 分页

- 全局 DRF 配置为 `PageNumberPagination`
- 但多数接口手写分页，说明业务层有自定义格式需求

#### 上传

- 内容附件、评论附件、私信附件、群资料文件均已支持

#### 消息通知

- `notifications/events.py`
- `notifications/community_tasks.py`

#### 缓存

- 板块树：`content/cache_utils.py`
- 搜索、榜单、Dashboard、管理统计、K 线、行情等均使用短 TTL 缓存

#### 定时任务

- Celery Beat 调度在 `settings.py`
- 任务落点在 `market_data/celery_tasks.py`
- 数据重建在多个 `management/commands/`

#### 性能打点

- `invest_backend/perf_timing.py` 提供 `@timed_api`

### 12.4 通用能力的依赖关系

- 首页、资产详情、组合收益 → 强依赖缓存与行情任务
- 点赞/评论/审核 → 强依赖通知事件
- 后台运营 → 强依赖 `reports` 聚合统计

## 13. 当前实现特点总结

### 13.1 优点

- 领域拆分基本合理，主轴清晰。
- 用户、内容、资产三大核心模型设计稳定。
- 行情同步、通知事件、积分、关注流已经开始抽出局部 service。
- 大量热点查询已有 `select_related/prefetch_related` 优化意识。
- 使用 `transaction.on_commit()` 处理副作用，是一个比较成熟的实现点。

### 13.2 不足

- view 过重问题明显。
- service 层覆盖不均。
- serializer 承担了较多业务组织工作。
- 返回格式缺少统一封装。
- 权限控制逻辑分散。
- 存在重复路由与重复视图。
- 日志与异常处理体系不完整。

### 13.3 可维护性

当前可维护性处于“能持续开发，但需要尽快收口规范”的阶段。

优点是业务基本都能定位到 app；缺点是进入 app 后，往往需要在超大 `views.py` 中继续人工辨识上下文。

### 13.4 扩展性

具备一定扩展性，尤其是：

- 新增业务 app
- 扩展行情任务
- 扩展通知事件
- 扩展统计重建

但如果继续无节制往已有 `views.py` 中堆逻辑，扩展成本会快速上升。

## 14. 后续开发建议

### 14.1 从“继续新增功能”的角度

#### 如果后续要新增接口

建议按以下顺序接入：

1. 明确归属 app
2. 先补 `urls.py`
3. 再加 serializer
4. 再写 view
5. 必要时抽 service
6. 若涉及副作用，再接通知/积分/on_commit

#### 如果后续要新增字段

至少同步检查：

1. `models.py`
2. 迁移文件
3. 相关 `serializers.py`
4. 相关 `views.py`
5. 前端 API 类型
6. 管理台或统计逻辑

#### 如果后续要新增权限规则

优先改：

1. `invest_backend/permissions.py`
2. `accounts/permissions.py`
3. 相关 view 的 `permission_classes`

同时尽量把零散的 `if request.user.role...` 收拢成可复用权限类。

#### 如果后续要新增认证方式

建议优先落在：

- `accounts/views.py`
- `accounts/serializers.py`
- `accounts/models.py -> UserSocialAccount` 或新增认证记录表
- `settings.py -> DEFAULT_AUTHENTICATION_CLASSES`

### 14.2 从“上线前整理”的角度

建议优先做四件事：

1. 补统一异常处理器与响应封装。
2. 处理重复路由与重复视图。
3. 把 `settings.py` 中敏感配置改为环境变量。
4. 抽取通用分页/权限/副作用基类，减少重复代码。

### 14.3 推荐的修改顺序

1. 配置安全与全局规范
2. 路由冲突与接口归并
3. 权限收敛
4. 大文件拆分
5. 性能热点优化
6. 再继续加新功能

### 14.4 哪些地方适合先重构再新增

- `accounts/views.py`
- `content/views.py`
- `portfolios/views.py`
- `reports/views.py`

先拆分再加功能，会显著降低后续维护成本。
