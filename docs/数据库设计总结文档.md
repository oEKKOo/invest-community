# 《股票基金投资社区系统数据库设计总结文档》

> 文档依据：扫描 `background/` 下各业务应用的 `models.py`、关键 `migrations`、`settings.py`、`views.py`、`serializers.py`、`tasks.py`、`management/commands`。  
> 分析口径：以 Django ORM 模型定义和迁移为准，数据库类型可确认的部分采用 Django 字段类型表述；若未直接看到真实 `SHOW CREATE TABLE` / 建表 SQL / ER 图，则物理 DDL 级细节标注为“待确认”。  
> 当前技术栈：`MySQL 8.x + Django ORM + Django REST Framework + JWT + Redis（可选） + Celery（可选）`。

## 1. 数据库整体定位

### 1.1 数据库在整个系统中的作用

本项目数据库是整个投资社区系统的核心持久化层，承担以下职责：

- 存储用户身份、权限、认证、投资偏好、社交关系等账号数据。
- 存储帖子、评论、板块、投票、点赞、收藏、附件、提及等社区内容数据。
- 存储资产基础信息、行情快照、K 线、持仓快照等投资与行情数据。
- 存储投资组合、组合持仓、组合评论、订阅收藏等结构化分享数据。
- 存储举报、审核队列、规则命中、行为统计等社区治理与分析数据。
- 存储通知、私信、群组等横向社交补充数据。

### 1.2 当前数据库主要承载的业务数据

当前数据库主要承载以下业务域数据：

- 用户与身份：`user`、认证申请、验证码、风险问卷、积分等级。
- 内容社区：`content`、`comment`、`board`、`content_asset`、`poll_*`、`favorite`、`like`。
- 资产行情：`asset`、`asset_quote_snapshot`、`asset_kline`、`data_job_log`。
- 投资组合：`portfolio`、`portfolio_asset`、`user_holding`、`holding_daily_snapshot`。
- 通知与社交：`notification`、`message_*`、`group_*`。
- 治理与统计：`report`、`moderation_*`、`community_metric_daily`、`topic_metric_daily`。

### 1.3 数据库与前端、后端、第三方服务的关系

- 与前端的关系：
  - 前端不直接访问数据库，而是通过后端 REST API 读取和写入数据。
  - 前端页面实体基本与数据库实体一一对应，例如用户、帖子、评论、组合、持仓、通知、群组、举报等。
- 与后端的关系：
  - 后端以 Django ORM 为主访问数据库。
  - 绝大多数查询、创建、更新、删除发生在各 app 的 `views.py`、`serializers.py`、`service`、`tasks`、`management commands`。
  - 少量高性能场景使用原生 SQL 或 migration 中的 DDL 语句。
- 与第三方服务的关系：
  - Finnhub / Tushare 的结果不会直接作为唯一数据源暴露给前端，而是会先落到 `asset_quote_snapshot`、`asset_kline` 等数据库表中。
  - Redis 在部分场景承担缓存和缓冲区角色，例如行情接口缓存、帖子浏览量缓冲。
  - Celery 主要承担通知、积分、关注流等副作用异步执行。

### 1.4 数据库在系统架构中的位置

数据库位于系统后端应用层之后、第三方行情服务之前，是系统的统一数据底座：

- 前端 -> DRF 接口 -> ORM / SQL -> MySQL
- 第三方行情服务 -> `market_data.tasks` / 管理命令 -> MySQL
- MySQL -> 经由 ORM / 聚合统计 -> 前端页面、管理后台、分析接口

从架构角度看，数据库并非仅支撑 CRUD，而是同时承担：

- 业务状态流转载体
- 统计指标沉淀层
- 第三方数据落地缓存层
- 治理审计留痕层

## 2. 数据库设计总览

### 2.1 当前数据库包含的核心业务域

当前数据库可拆分为 8 个主要业务域：

1. `accounts`：用户、关注、认证、隐私、积分、风险测评。
2. `content`：资产、板块、帖子、评论、互动、投票、附件。
3. `market_data`：行情快照、K 线、同步任务日志。
4. `portfolios`：投资组合、组合资产、个人持仓、收益快照。
5. `notifications`：站内通知。
6. `reports`：举报、审核规则、审核队列、命中日志、社区统计。
7. `groups`：群组、成员、入群审核、邀请、群贴、群文件。
8. `messages`：私信会话、消息、已读、附件。

### 2.3 各业务域之间的关系

- `accounts.User` 是全站主锚点，几乎所有业务表都直接或间接依赖它。
- `content.Asset` 是内容域、行情域、组合域之间的桥梁实体。
- `content.Content` 是社区内容中心，向评论、收藏、转发、审核、通知等多方向扩散。
- `portfolios.Portfolio` 是结构化内容中心，与 `Asset`、`UserHolding`、`Like`、`PortfolioComment` 强关联。
- `reports` 模块横向连接用户、内容、举报和统计，承担治理闭环。

### 2.4 整个系统的核心枢纽表

从数据库层面看，核心枢纽表主要有 5 张：

- `user`：用户中心主表，所有业务的身份锚点。
- `asset`：资产主表，是内容讨论、行情、持仓、组合的公共桥梁。
- `content`：帖子主表，是社区核心内容枢纽。
- `portfolio`：组合主表，是结构化投资分享枢纽。
- `asset_kline` / `asset_quote_snapshot`：承接第三方行情并为前台图表、组合计算、排名提供底层数据。

## 4. 核心表详细分析

### 4.1 表名：`user`

#### 4.1.1 表作用

- 解决什么业务问题：
  - 统一承载用户账号、身份、角色、状态、资料、积分、认证状态。
- 在系统中的定位：
  - 是全系统最核心的根表，所有模块围绕该表建立外键或业务关系。

#### 4.1.2 字段清单

| 字段 | 类型 | 可空 | 默认值 | 主键/唯一/索引/外键 | 含义 | 业务用途 | 关键字段 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `id` | `BigAutoField` | 否 | 自增 | 主键 | 用户主键 | 全站关联 | 是 |

## 5. 表关系与 ER 逻辑分析

### 5.1 核心实体

数据库的核心实体主要包括：

- 用户：`user`

### 5.2 实体关系逻辑

- `user -> content/comment/portfolio/report/notification`：典型一对多强依赖。
- `asset -> content_asset -> content`：资产与内容通过桥梁表形成多对多。
- `asset -> portfolio_asset -> portfolio`：资产与组合通过桥梁表形成多对多。
- `user -> user_holding -> holding_daily_snapshot`：用户持仓及其历史快照链路。
- `content -> comment -> reply`：内容评论树。
- `content -> moderation_queue_item -> report`：治理与审核闭环。
- `asset -> asset_quote_snapshot/asset_kline`：资产时序子表。

### 5.3 强依赖与弱依赖

- 强依赖关系：
  - `content.author_id -> user.id`
  - `comment.content_id -> content.id`
  - `portfolio.owner_id -> user.id`
  - `user_holding.asset_id -> asset.id`
  - `holding_daily_snapshot.holding_id -> user_holding.id`
- 弱依赖 / 业务代码依赖关系：
  - `like.target_type + target_id`
  - `report.target_type + target_id`
  - `notification.related_object_type + related_object_id`
  - `mention.source_type + source_id`

### 5.4 关联桥梁表

- `content_asset`
- `content_board`
- `portfolio_asset`
- `user_follow`
- `portfolio_subscription`
- `portfolio_favorite`
- `message_conversation_participant`
- `group_members`

### 5.5 冗余与关系深度问题

- 合理冗余：
  - `content.like_count/comment_count/favorite_count/view_count`
  - `portfolio.like_count/subscription_count`
  - `portfolio_asset.symbol/name`
  - `user.followers_count/following_count`
- 关系较深的链路：
  - 组合收益：`portfolio -> portfolio_asset -> asset -> asset_kline`
  - 持仓收益：`user_holding -> holding_daily_snapshot`，也会间接关联 `asset_kline`
  - 审核链路：`content -> moderation_hit / moderation_queue_item -> report`
- 需要重点注意的问题：
  - 多态表较多，数据库层无法直接保证目标对象存在。
  - 多个冗余计数字段依赖应用代码维护，一旦缺漏容易失真。

## 7. 数据访问与调用方式分析

### 7.1 调用方式

- 访问方式：
  - 后端主要通过 Django ORM 访问数据库。
  - 典型操作集中在 `views.py` 和 `serializers.py`。
  - 行情同步和统计重建在 `tasks.py`、`analytics_service.py`、`management/commands` 中完成。
- 是否有 service/repository 封装：
  - 有少量 service 化封装，但没有统一 repository 层。
  - 典型 service：
    - `accounts.user_score_service`
    - `accounts.feed_service`
    - `content.moderation_service`
    - `reports.analytics_service`
- 原生 SQL 使用情况：
  - migration `0010_content_fulltext_and_backfill.py` 使用原生 SQL 增加 MySQL FULLTEXT。
  - `fill_holding_snapshots.py` 使用 `INSERT IGNORE INTO ... SELECT` 批量补缺。
  - 少量工具脚本如 `fix_database.py` 使用裸 SQL。
- 事务使用情况：
  - 局部使用 `transaction.atomic()`，典型在关注、评论、点赞等操作上。
  - 但并非所有多表写操作都包裹事务。

### 7.2 典型数据读写流程

#### 7.2.1 发帖流程

- 输入：前端发帖页提交标题、正文、标签、资产、板块、投票、附件。
- 写路径：
  - 写 `content`
  - 写 `content_asset`
  - 写 `content_board`
  - 写 `content_meta`
  - 如为投票帖则写 `poll`、`poll_option`
  - 绑定 `content_attachment`
  - 调用 `moderation_service` 更新 `content.risk_*`
  - 命中时写 `moderation_hit`
  - 中高风险时写 `moderation_queue_item`
- 副作用：
  - `transaction.on_commit` 后发积分、关注流、提及通知
- 风险：
  - `ContentCreateSerializer.create()` 本身未显式包裹事务，多表写中途失败可能产生半成品数据。

#### 7.2.2 评论流程

- 写路径：
  - 写 `comment`
  - `Content.comment_count + 1`
- 副作用：
  - 发表评论积分
  - 评论通知
  - 提及通知
- 删除流程：
  - 将 `comment.status` 改为 `DELETED`
  - `Content.comment_count - 1`

#### 7.2.3 点赞 / 收藏流程

- 点赞：
  - `Like.get_or_create()`
  - 更新 `content.like_count` / `comment.like_count` / `portfolio.like_count`
  - 异步写 `notification`
- 收藏帖子：
  - `Favorite.get_or_create()`
  - 更新 `content.favorite_count`
- 组合订阅：
  - 写/删 `portfolio_subscription`
  - 更新 `portfolio.subscription_count`

#### 7.2.4 组合创建流程

- 写路径：
  - 写 `portfolio`
  - 批量写 `portfolio_asset`
- 读取路径：
  - 列表/详情查询 `portfolio`
  - `prefetch_related('assets', 'assets__asset')`
  - 动态聚合 `favorites_count`、`asset_count`
  - 通过 `asset_quote_snapshot` / `asset_kline` 构建收益指标
- 风险：
  - `PortfolioCreateSerializer.create()` / `update()` 未显式事务包裹。

#### 7.2.5 持仓与收益快照流程

- 持仓登记：
  - `UserHolding.update_or_create(user, asset)`
- 收益快照：
  - `fill_holding_snapshots` 用 SQL 从 `asset_kline` 批量回填 `holding_daily_snapshot`
- 读取：
  - 我的持仓、收益历史、组合持仓明细。

#### 7.2.6 行情数据流转

- 资产基础信息：
  - 导入脚本 / 管理命令写 `asset`
- 最新行情：
  - `quote_refresh()` 批量拉取后写 `asset_quote_snapshot`
  - 并回写缓存
- K 线：
  - `kline_sync()` / `_write_klines()` 批量写 `asset_kline`
- 前台接口：
  - 最新行情优先读缓存，其次读快照表
  - K 线只读数据库，不在请求内实时回补
  - 分时在缺数据时允许临时拉取并落库

#### 7.2.7 治理审核流程

- 自动审核：
  - 读取 `moderation_rule`
  - 写 `content.risk_*`
  - 写 `moderation_hit`
  - 必要时写 `moderation_queue_item`
- 举报：
  - 写 `report`
  - 后台处理时写 `report.status`、`handled_by` 等
  - 可联动 `moderation_queue_item`
- 人工决策：
  - 更新 `content.status`
  - 更新 `moderation_queue_item.status/decided_*`

#### 7.2.8 通知流程

- 点赞、评论、关注、提及、审核结果等业务事件触发后：
  - 通过 `notifications.events` 写 `notification`
- 特点：
  - 通知生成逻辑已从主业务中解耦，但仍以数据库表为落地点。

### 7.3 数据访问风险

- N+1 风险：
  - 大部分列表接口已使用 `select_related` / `prefetch_related` 优化。
  - 仍存在个别循环内按类型逐条取目标对象的场景，如“我的点赞记录”。
- 重复查询风险：
  - 组合列表会动态聚合 `favorites_count`、`asset_count`、收益指标，复杂页可能重复计算。
- 事务缺失风险：
  - 内容创建、内容更新、组合创建、组合编辑等多表写流程未统一加事务。
- 并发一致性风险：
  - 计数字段依赖应用层更新，局部虽然用了 `F()`，但删除与回退场景仍可能失真。
  - 组合订阅切换未显式事务包裹，存在并发写计数不一致风险。
- 查询困难风险：
  - 多态表虽然灵活，但跨类型联查和一致性排查困难。

## 8. 字段设计规范分析

### 8.1 主键设计

- 优点：
  - 绝大多数表统一使用 `BigAutoField`，主键风格统一。
- 结论：
  - 主键规范较统一，便于扩展。

### 8.2 时间字段规范

- 大多数表遵循：
  - `created_at`
  - `updated_at`
- 补充时间字段：
  - `published_at`
  - `read_at`
  - `reviewed_at`
  - `joined_at`
  - `started_at` / `finished_at`
- 结论：
  - 整体较统一，是当前数据库设计中的优点。

### 8.3 状态字段规范

- 常见状态字段：
  - `status`
  - `is_public`
  - `is_read`
  - `is_deleted`
  - `is_active`
  - `risk_level`
  - `identity_level`
- 问题：
  - 同类概念的枚举风格不统一。
  - 例如：
    - `content.status`：`DRAFT/PUBLISHED/...`
    - `comment.status`：`NORMAL/HIDDEN/DELETED`
    - `portfolio` 没有统一 `status`，用 `is_public`
    - `portfolio_comment` 用 `is_deleted`
    - `message` 也用 `is_deleted`
    - `user.status` 又是 `NORMAL/MUTED/BANNED`

### 8.4 命名风格

- 数据库命名整体采用 `snake_case`，较规范。
- 物理表名显式 `db_table`，避免 Django 自动命名不稳定。
- 但存在一些语义差异：
  - `groups` 使用复数名，其他多数表使用单数。
  - `like` 使用单数，容易和 SQL/语言关键概念混淆。
  - `risk_level` 在不同表语义不同。

### 8.5 布尔字段、枚举字段、审计字段合理性

- 布尔字段使用较多，简洁清晰：
  - `is_public`
  - `is_read`
  - `is_deleted`
  - `is_active`
  - `v_badge`
- 枚举字段问题：
  - 大量使用字符串枚举，便于可读性，但需要统一常量规范。
  - 风险等级有 `R1-R5`、`LOW/MEDIUM/HIGH`、`Low/Medium/High` 三套表达。
- 审计字段：
  - 整体较完整，但不同表“谁审核/谁处理”的字段名存在 `reviewed_by`、`handled_by`、`decided_by` 多套命名。

### 8.6 历史遗留字段

- 明确的历史兼容字段：
  - `portfolio_asset.symbol`
  - `portfolio_asset.name`
- 可能需要统一的重复语义字段：
  - `user.risk_level`
  - `user_invest_profile.risk_level`
  - `portfolio.risk_level`
  - `content.risk_level`

## 9. 数据一致性与约束分析

### 9.1 依赖外键 / 唯一约束保证一致性的地方

- 关注关系：`user_follow`
- 帖子收藏：`favorite`
- 组合订阅：`portfolio_subscription`
- 投票去重：`poll_vote`
- 持仓唯一：`user_holding`
- 持仓快照唯一：`holding_daily_snapshot`
- 资产业务唯一：`asset(asset_type, code, market)`

### 9.2 更多依赖业务代码保证一致性的地方

- `like` 多态关联对象存在性。
- `report.target_type/target_id` 目标存在性。
- `notification.related_object_*` 跳转对象存在性。
- 计数字段：
  - `content.like_count/comment_count/favorite_count/view_count`
  - `portfolio.like_count/subscription_count`
  - `user.followers_count/following_count`

### 9.3 孤儿数据风险

- 高风险：
  - `like`
  - `report`
  - `notification`
  - `mention`
- 原因：
  - 这些表使用“类型 + id”的多态关联，而非数据库外键。

### 9.4 重复数据风险

- `portfolio_asset` 在 `asset_id` 为空的历史兼容模式下，可能出现重复语义记录。
- `asset_quote_snapshot` 本身允许重复快照，是设计选择而非错误，但需要保留期管理。
- `asset_kline` 通过联合唯一约束避免重复，较规范。

### 9.5 删除联动问题

- `content`、`comment`、`portfolio` 大多用物理删除或级联删除。
- `comment` 又通过 `status='DELETED'` 软删除。
- `portfolio_comment` 和 `message` 用 `is_deleted`。
- `content_attachment` / `comment_attachment` 允许先上传再绑定，因此外键可空。

结论：

- 当前系统存在“逻辑删除与物理删除混用”的典型问题。
- 后续维护时必须先确认目标模块采用哪一类删除策略，否则很容易引发统计错误或数据遗留。

### 10.1 高频查询表

- `comment`
- `asset`
- `asset_quote_snapshot`
- `asset_kline`
- `portfolio`
- `notification`
- `user_follow`

### 10.2 高频写入表

- `comment`
- `like`
- `favorite`
- `notification`
- `asset_quote_snapshot`
- `asset_kline`
- `holding_daily_snapshot`
- `follow_feed_item`

### 10.3 后续增长最快的表

- `asset_kline`
- `asset_quote_snapshot`
- `comment`
- `like`
- `notification`
- `holding_daily_snapshot`
- `follow_feed_item`
- `moderation_hit`

### 10.4 当前索引设计是否支撑未来业务

- 优点：
  - 内容、资产、行情、审核队列、持仓快照等主要热点路径都有针对性索引。
  - 后期迁移明显补充了高频路径索引，如：
    - `content_asset(asset, -created_at)`
    - `asset_quote_snapshot` 榜单索引
    - `holding_daily_snapshot` 快照索引
    - `portfolio_subscription` 时间索引
- 不足：
  - 热门内容按 `like_count/comment_count` 排序的路径还可继续优化。
  - 用户、通知、举报、消息等表仍偏“基础索引”，没有更细的组合索引。

### 10.5 分页、排序、条件过滤隐患

- `asset_quote_snapshot` 榜单查询依赖子查询取最新快照，数据量大后成本会上升。
- `content` 热门排序若同时叠加状态、板块、资产过滤，可能需要更细复合索引。
- 组合详情和收益指标依赖运行时计算，页内组合数变多后 CPU 与 IO 开销会增加。

### 10.6 冗余字段换取查询效率

当前已经采用了较多“冗余字段换性能”的思路：

- 内容和组合上的计数字段。
- 组合资产中的 `symbol/name` 冗余。
- 用户粉丝/关注计数字段。
- 日统计表、话题统计表。

这是合理的，但前提是：

- 必须有稳定的回填和校正机制。
- 必须明确哪些字段是“权威值”，哪些字段是“缓存值”。

### 10.7 是否需要分表、归档、快照、缓存

- 当前阶段：
  - 不必立即分表，毕设规模和当前项目体量通常可承受。
- 建议优先做：
  - 行情快照保留期清理
  - K 线按周期/日期归档策略预留
  - 浏览量缓冲持续使用 Redis
  - 热点榜单、组合收益指标短缓存
- 若未来数据增长明显：
  - `asset_kline` 可按市场或周期归档
  - `asset_quote_snapshot` 可按日期分区或定期归档
  - 日志类表可转冷数据存储

### 10.8 当前数据库设计扩展性评价

- 总体评价：
  - 扩展性中上，足以支撑毕业设计与中小规模社区产品原型。
- 扩展优势：
  - 领域划分清晰。
  - `asset` 作为桥梁实体设计合理。
  - 快照 / 统计 / 日志表已具备工程化意识。
- 主要扩展阻力：
  - 多态表太多。
  - 状态字段规范不统一。
  - 多表写事务边界不统一。

## 11. 核心数据库设计优缺点总结

### 11.1 当前设计优点

- 业务域划分清晰，表命名基本规范。
- 采用自定义用户模型，便于长期扩展。
- `asset` 作为全局桥梁实体，设计很关键且合理。
- 内容域、组合域、行情域之间边界较清楚。
- 大量使用 `created_at/updated_at`，审计基础较好。
- 已有日志表、统计表、快照表，工程完整度较高。
- 热点路径后期已有性能补索引动作，说明设计在持续演进。

### 11.2 当前设计不足

- 多态关联较多，数据库级完整性不足。
- 冗余计数字段较多，但统一校准机制还不够显式。
- 删除策略不统一，软删和硬删混用。
- 枚举值和状态字段命名风格不统一。
- 部分多表写流程缺少事务包裹。
- 风险等级、状态等级存在多套语义体系。

### 11.3 哪些地方设计较规范

- 主键统一。
- 时间字段统一。
- 大多数中间表都有唯一约束。
- 行情数据表索引设计较贴合真实查询路径。
- 审核队列、命中日志、统计表分层明确。

### 11.4 哪些地方耦合较高

- `user` 与所有模块高度耦合。
- `asset` 同时连接内容、行情、组合、持仓，属于必要高耦合中心表。
- `content` 同时承载发布、审核、统计、搜索、互动，是高耦合主表。

### 11.5 哪些地方字段职责混乱

- `risk_level` 在不同表含义不同。
- `status` 在不同表语义粒度不同。
- `portfolio_asset.symbol/name` 既是展示字段又带兼容职责。
- `notification.related_object_*` 只有跳转用途，不具备真正实体关系能力。

### 11.6 哪些地方后续最容易改坏

- 内容创建/更新流程，因为涉及多张表和审核副作用。
- 点赞/收藏/评论计数字段，因为涉及冗余同步。
- 资产代码解析逻辑，因为 `assetCodes` 目前只按 `code` 校验。
- 组合资产表，因为兼容字段与强 FK 并存。
- 多态表，因为加新类型时容易漏改通知、权限、统计、删除逻辑。

## 12. 后续开发建议

### 12.1 继续新增功能时的建议

- 新增字段时：
  - 先改 `models.py`
  - 再生成 migration
  - 再检查相关 serializer、view、统计、缓存、排序字段
- 新增业务模块时：
  - 优先判断是否应该依附于 `user`、`asset`、`content`、`portfolio` 这四个主轴
  - 避免新建“语义重复的中心表”
- 新增用户关系能力时：
  - 尽量复用 `user_follow` 体系
  - 若是黑名单、好友、订阅标签，可新增关系表而非塞进 `user`
- 新增审核流时：
  - 优先复用 `report`、`moderation_rule`、`moderation_queue_item`
  - 保持“命中日志 -> 队列 -> 决策”三层结构
- 新增资产数据时：
  - 优先扩展 `asset.meta_json`
  - 只有字段稳定且会高频筛选时再升到主列

### 12.2 上线前整理建议

1. 统一状态字段规范。
2. 梳理软删与硬删策略。
3. 为多表写路径补事务。
4. 为冗余计数字段补校准脚本。
5. 检查多态表孤儿数据。
6. 检查 `assetCodes` 跨市场歧义。
7. 检查真实数据库中 FULLTEXT 和新增索引是否已执行。

### 12.3 推荐的修改顺序

1. 先做“规范性整理”：
   - 状态字段、删除策略、命名清理。
2. 再做“事务与一致性”：
   - 内容发布、组合创建、订阅切换。
3. 再做“性能优化”：
   - 热门列表索引、榜单最新快照查询、慢 SQL 排查。
4. 最后再做“新增模块”。

### 12.4 哪些地方适合先重构再继续新增

- `like` / `report` / `notification` 多态关联。
- `portfolio_asset` 兼容字段体系。
- `risk_level` / `status` 的枚举规范。
- 统计与冗余计数字段的校准机制。
